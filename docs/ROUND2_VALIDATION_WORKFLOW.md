# M4 訓練後驗證與合計預算

2026-10-18。這份文件補充第二輪的執行銜接，不修改事前模型、資料、選參規則或候選門檻。原始規則 `ce0fc1a`、開跑前補充 `f5f83bc` 與 L 型時間修訂 `ee4a066` 保留原樣。本入口在首次正式密度驗證前提交、推送並核對來源。

## 何時啟動

`run_round2_validation_workflow.py` 只接受新訓練控制器的 `awaiting_validation` 狀態。S、L 各完成 30 輪並退出後，才能取得同一把 M4 程序鎖。訓練中提前呼叫會被拒絕，不啟動另一個 GPU 工作。

開始前，核對原始、時間修訂、分析與驗證排程四份來源憑據。再檢查兩種密度頭的全部訓練歷史、每輪圖片數、有限數值及凍結參數雜湊；從 train-holdout MAE 重選最佳輪次，同分取較早者，並核對 best／last 檢查點 SHA-256。任何失敗或不完整訓練都不能進入正式 val。

## 固定執行順序

1. S42：32 圖密度 gate → 獨立核算 → 1,286 圖完整 val → 獨立核算。
2. L42：相同的 gate、完整 val 與核算。
3. 類別兩折選寬度及融合 → 折外結果獨立核算。

每個步驟都必須有正確數量的完成紀錄；程式正常退出本身不算通過。Gate 核算失敗便停止，不能繼續完整 val。融合產生器原有的 `independent_crossfit_audit=pending` 保持原樣，另以 `audit.json=passed` 證明後續核算完成。

最後狀態為 `awaiting_seed_sensitivity`，只代表 seed 42 的這段流程完成。種子 43／44、條件式微調、M2／M3 第二版及最終凍結仍須按協議接續；本入口不執行 test。

## 30 小時怎麼算

帳本為 `results/round2-v1/m4_budget_ledger_v1.json`。首先把訓練控制器的 `spent_seconds` 原樣導入一次：這個數字已包含前置核驗、容量試驗及 S42、L42，不能再逐項加一次。也會對照兩個 head 的耗時與修訂前保存的前置耗時，防止遺漏。

其後逐步記錄啟動時間、允許時間、實際耗時、結果及證據雜湊。這段驗證中的 CPU 核算、融合與銜接核驗也扣除同一預算，作保守計算。每步最多 90 分鐘，若合計剩餘更少便採剩餘額度；其中預留 10 秒供程序終止及結算，不作額外運算。CPU 步驟的 90 分鐘是操作超時限制，不是新增模型選擇規則。

失敗、超時與中止的實際耗時照樣入帳。超限結果不被接受；剩餘不足或帳本有尚未結算的工作時停止。被強制中斷後留下的 active 記錄，必須先查明程序及已花時間，不能靠重開帳本重置預算。

## 中斷與重複啟動

排程狀態另存 `validation_workflow_v1.json`，不回寫訓練控制器或早期證據。所有子步驟循序執行；超時時只終止該步驟自己的程序群組。既有排程、帳本、輸出目錄或日誌都不自動覆蓋，也不自動接納部分輸出。完整錯誤日誌留在伺服器，公開紀錄只保留錯誤類型與去識別化證據。

CPU 測試涵蓋預算重複導入、未完成的訓練、不完整結算、失敗耗時、剩餘額度收緊、非有限值、程序鎖競爭、非零退出、超時，以及檢查點篡改和錯誤選輪。這些測試驗證排程邊界，不代表真實密度圖或計數準確度已通過。

執行時，在伺服器專案根目錄以其 Python 環境呼叫：

```sh
.venv/bin/python scripts/run_round2_validation_workflow.py --root .
```

仍須先確認訓練控制器已完成、來源憑據已同步及沒有其他 GPU 程序；不能依舊的 `workflow.json` 重開工作。
